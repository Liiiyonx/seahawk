# 探海灵眸 SeaSight 总控计划书

> 版本：2.0  
> 编制日期：2026-09-18  
> 参赛赛道：海洋科创 / 海上智能装备与无人系统，兼顾数字赋能现代渔业与海洋绿色低碳创新  
> 文档定位：研发、产品、商业、答辩、验收和智能体分派的唯一总控基线

## 0. 先给结论

探海灵眸不是一个单台清洁船项目，而是一套面向县域海上环卫治理的“感知、决策、执行、核算”区域级软件与装备系统。当前项目已经具备较强的软件工程底座：事件接入、幂等去重、时序降误报、空间派单、任务状态机、MQTT 上下行、ACK 超时重派、Redis Streams 消费与 PEL 回收、日报聚合、认证、审计和可视化页面均有真实代码与自动化测试。

但项目距离“经得起智能体开发和创新创业比赛严审”仍有明确缺口。当前最重要的三个缺口不是页面数量，而是：

1. 智能体仍是静态目录和静态状态，尚无可运行、可观察、可回放、可重规划的 Agent Runtime。
2. 真实海域数据、机器人硬件、现场试点和客户协议尚未形成证据链。
3. 商业数字目前是测算，不是订单、收入或采购结论，必须继续按测算口径表达。

因此，本计划书不承诺“必得国奖”。国奖无法由任何文本或单方面努力保证，但可以通过真实问题、技术深度、可复现证据、产品闭环、商业验证和现场表达，把项目提升到稳定的国奖候选水平。目标是把当前约 61/100 的评审基线提升到 86/100 以上的候选区间，并消除所有“一问就穿”的诚信风险。

## 1. 证据分级与表述纪律

全文和对外材料统一使用以下五级证据。任何能力描述必须能对应到证据级别，不能把规划写成现状。

| 级别 | 含义 | 可对外使用的表述 |
| --- | --- | --- |
| E0 | 只有想法、文档或接口草案 | “规划中”“拟建设” |
| E1 | 有代码、单元测试或确定性仿真 | “已实现，已通过软件测试” |
| E2 | 多模块软件联调，使用合成数据或模拟设备 | “已完成合成环境闭环验证” |
| E3 | 真实设备、真实海域或真实用户参与验证 | “已完成现场验证” |
| E4 | 有合同、订单、回款、验收报告或复购 | “已形成商业验证” |

以下四类表述在项目完成 E3 或 E4 前禁止使用：

- 禁用“视觉大模型已经部署”，当前真实路线是 OpenCV 传统视觉检测。
- 禁用“机器人已实现 7×24 自主清理”，当前只有软件链路和合成或模拟验证。
- 禁用“智能体已经在线协同”，当前必须写成“正在建设可运行 Agent Runtime”。
- 禁用“已有客户、订单、收入、试点成效”，除非附件中存在合同、协议、验收或财务凭证。

### 2.1 评委最可能提出的十个问题

1. “你们说检测有 76% 抑制率，抑制了什么，分母是什么，真海况测过吗？”
2. “六个智能体分别运行在哪里，谁规划、谁调用工具、失败后如何重规划？”
3. “如果没有大模型或外网，系统还能工作吗？”
4. “机器人是否已经做出实物，最大抗风浪等级、续航、载重和故障率是多少？”
5. “平台发现垃圾之后，为什么不是人工点一下派单，而必须是智能体？”
6. “政府现有每吨清理成本是多少，你们的报价依据来自哪里？”
7. “本地数据集现在有多少张，标注一致性如何，是否存在独立测试集？”
8. “系统如何防止 Agent 误派、重复派单和越权操作？”
9. “试点协议、意向书、测试报告或验收报告在哪里？”
10. “如果机器人离线、MQTT 断连、模型误报或 Redis 故障，用户看到什么，谁负责兜底？”

### 2.2 直接影响奖项等级的红线

- 任何静态状态被包装成实时运行状态。
- 用 MD5 伪推理结果冒充真实模型输出。
- 将测算价格写成客户成交价。
- 将合成海面测试写成真实海域验收。
- 只有“AI”“大模型”“智能体”标签，没有输入、工具、观察、验证和终止条件。
- 答辩系统无法现场复现，或者只能播放预录视频。
- 文档中的测试数量、准确率、成本与当前代码或数据不一致。
- 项目没有明确购买者、预算科目和商业模式。

## 3. 产品经理视角：谁买、谁用、为什么持续使用

### 3.1 用户和购买者不是同一个人

| 角色 | 核心任务 | 当前痛点 | 产品承诺 | 是否付费方 |
| --- | --- | --- | --- | --- |
| 县海洋与渔业主管部门 | 监管、考核、汇报、专项治理 | 数据分散，治理成效难量化，缺少统一台账 | 一张图掌握事件、任务、清理量和风险 | 是 |
| 沿海乡镇操作员 | 发现、派单、督促、闭环 | 巡查靠人，跨队伍协调靠电话，过程难追溯 | 少点几次、少打几个电话，异常自动到人 | 预算执行方 |
| 海上环卫作业队 | 接单、航行、打捞、回传 | 空驶多、临水风险高、任务优先级靠经验 | 减少空驶和重复航行，保留人工接管 | 直接用户 |
| 养殖户或渔民 | 上报、回收、领取补贴 | 上报流程不透明，回收收益兑现慢 | 低门槛上报，记录可查，积分或补贴可核销 | 参与方 |
| 平台管理员 | 设备、权限、阈值、审计 | 设备状态和系统异常不可见 | 全链路观测、回放、审批和审计 | 运维方 |
| 算法或运维工程师 | 模型、数据、故障处理 | 离线模型与线上系统割裂 | 数据闭环、版本管理、评测和热更新 | 技术用户 |

项目当前的主要购买者是县级主管部门或乡镇政府，主要高频用户是乡镇操作员和海上环卫作业队，养殖户是治理网络的参与节点，不是短期内的主要收款对象。

### 3.2 核心 Job To Be Done

> 当辖区海面出现影响航道、养殖、岸线和旅游环境的漂浮垃圾时，我要在有限人力和预算下，快速确认问题、派出合适设备、跟踪执行过程，并向上级证明问题已经闭环，而不是只看到一堆视频和告警。

产品必须回答四个连续问题：

1. 问题是否真实存在，证据是什么？
2. 应该派谁、何时去、代价是多少？
3. 执行是否顺利完成，失败后怎么处理？
4. 最终清理了什么，花了多少钱，是否值得继续采购？

### 3.3 产品主线

```text
发现
  摄像头/无人机/人工上报
    -> 证据帧、类别、置信度、空间位置、时间

确认
  时序验证、空间聚类、历史对比
    -> 形成可信事件，抑制单帧误报

决策
  Agent 读取事件、设备、任务、天气和历史
    -> 生成计划，经过策略守卫和审批策略

执行
  MQTT 下发、ACK、导航、作业、异常监控
    -> 任务状态和轨迹持续回传

验收
  机载复核、证据回传、重量录入、人工确认
    -> 事件、任务、材料和费用一致

核算
  日报、月报、热力图、成本和服务绩效
    -> 支撑考核、续约和扩大投放
```

### 3.4 产品北极星指标

第一阶段北极星指标不使用“识别框数量”或“页面访问量”，而使用：

> 单位有效成本下完成闭环并经过证据确认的垃圾清理量。

计算公式：

```text
单位闭环成本 = 设备折旧 + 能源 + 运维 + 人工协同 + 通信
               / 已验收清理量

有效闭环率 = 状态为 done 且存在复核、重量、时间和证据的任务数
             / 已派发任务数
```

在当前阶段，先建立可计算的数据链路，再使用真实试点数据替换估算值。

## 5. 智能体开发比赛的核心方案

### 5.1 为什么不能继续把模块叫“智能体”

识别、调度、报表、巡检、告警和审计都有价值，但它们是能力模块，不是独立智能体。真正的智能体必须具备：

- 从目标出发生成计划。
- 在受控工具集合中选择并调用工具。
- 读取工具结果并观察环境变化。
- 判断计划是否成功，失败时重规划。
- 在关键动作前执行策略校验和人工审批。
- 在明确条件满足后终止，并记录终止原因。
- 全过程可追踪、可回放、可评测、可追责。

项目的智能体叙事必须从“有六个卡片”转为“一个可运行治理 Agent 内核，驱动多个专业工具和受限角色”。

### 5.2 推荐架构

```text
                     Agent Runtime
  事件/人工/定时触发 -> Run Manager -> Planner
                                      |
                              Policy Guard
                                      |
                             Tool Executor
                  +-------------------+-------------------+
                  |                   |                   |
              设备查询            空间派单            任务操作
                  |                   |                   |
              证据读取            指标查询            通知审批
                  +-------------------+-------------------+
                                      |
                                 Observer
                                      |
                              Verifier / Evaluator
                                |             |
                              成功           失败
                                |             |
                              终止        Replanner
                                \             /
                                 Trace + Memory
```

### 5.3 运行状态机

```text
created
  -> planning
  -> waiting_policy
  -> waiting_approval
  -> executing
  -> observing
  -> verifying
  -> succeeded
  -> failed
  -> cancelled
  -> expired
```

每次重规划必须产生新 step，不允许覆盖历史步骤。失败原因必须结构化保存，例如 `no_robot_available`、`tool_timeout`、`policy_denied`、`approval_rejected`、`task_conflict` 或 `max_steps_exceeded`。

### 5.4 Agent 角色

建议第一阶段只落一个通用编排器和五个受限专业角色，避免为了“多智能体”而人为拆碎职责。

| 角色 | 目标 | 允许工具 | 关键约束 |
| --- | --- | --- | --- |
| 总控编排器 | 判断事件是否处理，组织计划并验证结果 | 查询、派单、任务、通知、审批 | 必须有最大步数、超时和终止原因 |
| 视觉复核员 | 复核事件证据与类别可信度 | 证据读取、历史事件查询 | 不能直接修改原始检测结果 |
| 调度规划员 | 选出机器人并生成派单计划 | 设备、空间、任务工具 | 电量、距离、仓容、辖区硬约束 |
| 作业监督员 | 观察 ACK、轨迹、作业进度和异常 | 任务、遥测、MQTT 状态 | 超时只回退或建议，不绕过状态机 |
| 异常审查员 | 识别误报、重复任务、设备异常 | 审计、评测、通知工具 | 可建议驳回，不能静默删数据 |
| 报表分析员 | 生成日报和治理绩效 | 聚合、报表、导出工具 | 只能从已确认业务数据计算 |

### 5.5 工具契约

所有工具使用统一接口，包含名称、版本、输入 Schema、输出 Schema、权限、超时、幂等键、审计事件和错误码。

| 工具 | 用途 | 关键输出 | 风险级别 |
| --- | --- | --- | --- |
| `event.get` | 读取事件和证据 | 事件、类别、置信度、位置 | 只读 |
| `device.query_available` | 查询可用机器人 | 距离、电量、仓容、状态 | 只读 |
| `dispatch.plan` | 生成候选派单方案 | 方案、评分、拒绝原因 | 只读 |
| `task.create_or_merge` | 建单或合并任务 | task_id、动作、状态 | 需幂等 |
| `task.transition` | 状态迁移 | 新状态、时间戳 | 需策略守卫 |
| `mqtt.send_task` | 下发设备指令 | 发送结果、消息 ID | 需审批或自动策略 |
| `mission.observe` | 查询任务和遥测 | ACK、轨迹、电量、仓容 | 只读 |
| `human.request_approval` | 请求人工审批 | 审批单 ID、状态 | 强制审计 |
| `metric.query` | 查询治理指标 | 指标值、口径和时间窗 | 只读 |
| `report.generate` | 生成日报 | 结构化报表和导出记录 | 需数据完整校验 |

### 5.6 确定性内核与可选大模型增强

项目不能依赖外网或商业大模型才能完成核心治理闭环。正确设计是：

- 确定性控制器负责状态、规则、工具调用、超时、重试和终止。
- 规则策略先给出可验证的基线决策。
- 大模型只用于意图理解、异常解释、计划候选生成和自然语言总结。
- 大模型输出必须经过 JSON Schema、策略守卫和工具白名单。
- 模型不可用时自动退回规则模式，系统核心能力不下降。
- 所有模型调用记录版本、耗时、成本和输入输出摘要，不保存不应保存的隐私数据。

这既符合工程可靠性，也避免项目被质疑为“套壳大模型”。

### 5.7 记忆设计

记忆不是把全部历史塞进提示词，而是分层的业务数据：

| 记忆类型 | 内容 | 作用 | 保留策略 |
| --- | --- | --- | --- |
| 工作记忆 | 当前 run 的计划、步骤和观察 | 完成本次任务 | 随 run 保留 |
| 情景记忆 | 历史上类似事件和处理结果 | 相似案例检索 | 按业务保留期 |
| 语义记忆 | 点位、潮汐、垃圾类别、设备特征 | 辅助规划 | 版本化管理 |
| 策略记忆 | 规则、阈值和人工纠正 | 防止重复错误 | 必须审批后生效 |
| 评测记忆 | 固定场景、期望轨迹和失败样本 | 回归测试 | 永久版本化 |

记忆写入必须区分“事实”“推断”和“人工确认”，禁止把模型猜测写成事实。

### 5.8 人工审批

以下情况必须人工审批：

- 超出日常策略的距离、成本或机器人数量。
- 低置信度事件触发高成本任务。
- 跨乡镇辖区调度。
- 机器人故障状态下的强制下发。
- 批量任务、敏感数据导出和阈值修改。

普通、低风险、同辖区、满足全部硬约束的派单可自动执行，但必须产生的证据包括：

- 触发来源。
- 策略版本。
- 候选方案和淘汰原因。
- 工具调用结果。
- 最终动作。
- 结果验证和终止原因。

新增以下核心表，字段由 Alembic 管理：

### 5.11 前端信息架构

智能体页面改为四个区域：

1. 运行总览：活跃 run、成功率、失败原因、P95 耗时、待审批数。
2. 实时轨迹：按步骤展示计划、工具调用、观察、验证、重规划和终止。
3. 工具与策略：工具可用性、版本、权限、策略版本和阻断原因。
4. 评测与回放：固定场景、期望结果、最近运行差异和回归状态。

界面不得展示伪造的“在线”“运行中”或收益数字。后端不可用时必须显示真实错误和降级状态。

### 5.12 Agent 测试矩阵

至少覆盖以下场景：

| 场景 | 预期结果 |
| --- | --- |
| 事件可信、机器人可用 | 自动计划、派单、观察、完成 |
| 无机器人可用 | 不误报成功，记录原因，等待补派 |
| 工具超时 | 有重试上限，能重规划或安全失败 |
| 机器人 ACK 超时 | 回退任务并换车，不重复建单 |
| 策略拒绝 | 动作被阻断，产生结构化原因 |
| 审批拒绝 | run 终止，不发送设备指令 |
| 重复触发同一事件 | 幂等，复用 run 或任务 |
| 模型不可用 | 确定性规则模式继续工作 |
| 达到最大步数 | 安全终止，不无限循环 |
| 轨迹完整性 | 每一步有状态、摘要、时间和结果 |

### 5.13 Agent 评测指标

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 任务成功率 | 期望业务结果达成的 run 比例 | 固定评测集不低于 95% |
| 策略违规率 | 被守卫发现但工具已执行的违规次数 | 0 |
| 工具调用正确率 | 参数、权限、幂等均正确的调用比例 | 不低于 99% |
| 无效循环率 | 超步数或重复无进展步骤的 run 比例 | 低于 1% |
| 恢复成功率 | 可恢复异常中成功恢复的比例 | 不低于 90% |
| P95 决策耗时 | 从触发到首个可执行计划的耗时 | 规则模式目标低于 2 秒 |
| 人工接管率 | 需要人工完成关键决策的任务比例 | 试点后持续下降 |
| 单次决策成本 | 模型、工具和基础设施成本 | 可量化、可设预算上限 |

## 6. 感知、执行与数据闭环

### 6.1 当前识别路线

当前采用 OpenCV 传统视觉检测，包括 ROI、背景建模、白亮通道、暗色通道、形态学、轮廓规则、类别规则和伪置信度。它的价值是零数据依赖、可解释、纯 CPU 可运行，但它不是最终模型路线。

对外必须同时说明：

- 当前实现是 OpenCV 真检测，不是 MD5 stub。
- 合成数据的 76% 抑制率只证明时序链路有效。
- 真实精度、误报率和跨天气泛化尚未验证。
- YOLO 或轻量分类器是数据积累后的候选路线，不写“已经部署”。

### 6.2 数据集建设

第一阶段只聚焦可定义、可复现的场景：

- 主类别：EPS 泡沫浮球和碎片。
- 次类别：塑胶浮球、瓶体、废旧渔网、绳索和饵料包装。
- 场景：白天、平潮、晴天、阴天、弱反光优先。
- 负样本：浪花、反光、固定浮球阵列、船只、水鸟、岸线物体。
- 每个样本记录点位、时间、天气、潮汐、设备、镜头和标注版本。

数据分集不得随机泄漏：

```text
训练集：用于模型拟合
验证集：用于调参和阈值选择
独立测试集：按日期和点位隔离，只用于最终评测
现场盲测集：交付答辩前封存，现场演示使用
```

### 6.3 独立评测指标

每个类别分别报告：

- Precision。
- Recall。
- F1。
- AP50 和 AP50-95。
- 每千帧误报数。
- 事件级发现率。
- 从真实目标出现到确认事件的时间。
- 按天气和光照分层的指标。
- 置信区间和样本量。

禁止只报告一个“准确率”，也禁止用训练集结果对外。

### 6.4 机器人执行边界

平台负责目标点、状态、任务和证据，不冒充已经完成机器人自主导航、避障、自动返航和自动充电。与硬件组的接口至少包括：

| 接口 | 平台发送 | 机器人回传 |
| --- | --- | --- |
| 任务 | task_id、目标经纬度、优先级 | ACK、拒单原因 |
| 状态 | 查询或控制指令 | navigating、collecting、done、fault |
| 遥测 | 无 | 位置、电量、航速、仓容、故障码 |
| 证据 | 上传地址或上传凭据 | 作业前后影像、重量、复核结果 |

真实硬件达到 E3 前，宣传中统一使用“机器人协作单元”和“作业端接口”，不使用“完全自主无人船”。

## 7. 核心指标体系

### 7.1 感知指标

| 指标 | 口径 | 当前状态 | 目标证据 |
| --- | --- | --- | --- |
| 泡沫 precision | 独立测试集，按目标匹配 | 未测 | 不低于 80% |
| 泡沫 recall | 独立测试集，按目标匹配 | 未测 | 不低于 70% |
| 事件级误报率 | 确认事件中现场不存在的比例 | 未测 | 由试点数据决定门槛 |
| 发现时延 | 真实目标出现到事件确认 | 合成环境可测 | 形成分层统计 |
| 降误报抑制率 | 被时序过滤的检测数 / 输入检测数 | 合成数据约 76% | 真实视频重新标定 |

以上数值是研发目标，不是当前成绩。

### 7.2 调度与执行指标

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 派单成功率 | 形成合法有效任务的派单尝试比例 | 不低于 99% |
| 重复建单率 | 同事件产生的非预期重复任务 | 0 |
| ACK 成功率 | 设备收到任务并确认的比例 | 按实网统计 |
| ACK 时延 | 下发到 ACK 的耗时 | P95 目标低于 5 秒 |
| 重派成功率 | ACK 超时后可重新分配的比例 | 不低于 90% |
| 任务闭环率 | 形成完整状态、重量和证据的任务比例 | 不低于 90% |
| 设备在线率 | 可用时间 / 应服务时间 | 按试点考核 |
| 数据完整率 | 必填业务字段齐全的工单比例 | 不低于 99% |

### 7.3 商业与治理指标

| 指标 | 定义 | 用法 |
| --- | --- | --- |
| 每吨综合清理成本 | 总成本 / 已验收吨数 | 与人工清运成本比较 |
| 每闭环任务成本 | 总成本 / 完整闭环任务数 | 判断调度效率 |
| 每监测点年成本 | 硬件折旧 + 通信 + 维护 | 报价基础 |
| 空驶距离占比 | 无有效作业航行距离 / 总航行距离 | 衡量 Agent 调度价值 |
| 治理响应时延 | 发现到任务开始 | 政府考核指标 |
| 纠纷或复核率 | 被质疑或需复查的任务比例 | 数据可信度 |

不能用单一“清理了 X 吨”替代成本和闭环质量。

## 8. 商业模式与市场验证

### 8.1 商业逻辑

项目不试图创造一个完全不存在的新预算，而是切入政府已经在支出的人工巡查、临水打捞、设备维护和治理汇报流程。第一阶段的核心产品是“智能监测与调度服务”，不是单纯卖船。

三种收入模式：

1. 政府购买服务：监测点位服务费、任务运营费、按验收清理量计费。
2. 设备销售或租赁：面向景区、环保公司、园区和其他作业单位。
3. 数据与生态服务：环境数据订阅、治理绩效接口和未来的生态价值服务。

### 8.2 连江首发策略

首发场景不追求全县铺开，而是选择 1 个乡镇、1 至 2 个固定点位和 1 个可控作业单元。成功判据不是签约金额，而是：

- 有明确责任人和使用流程。
- 能连续运行一个有效周期。
- 产生事件、任务、清理和异常的真实记录。
- 形成用户签字或用印的试用反馈。
- 能算出至少一次真实单位成本。

### 8.3 商业数字纪律

当前 `docs/business-model.md` 中的 1.52 万元原型机成本、875 元每吨人工成本参照、650 元每吨服务价、11 万元试点年营收和三年回报均为测算。正式计划书应增加：

- 每项数字的来源类型：公开资料、供应商询价、用户访谈或团队假设。
- 询价日期和报价有效期。
- 敏感性上下限。
- 若核心变量不成立的替代方案。

在取得采购意向、试点协议、验收单或回款前，所有数字必须标记“测算，不构成成交承诺”。

### 8.4 市场路径

市场范围按证据逐级解锁：

1. 连江单乡镇试点：验证问题、流程、成本和用户价值。
2. 连江多乡镇复制：验证跨点位调度和运维。
3. 福州与福建沿海复制：验证气候、监管和预算差异。
4. 全国沿海及内陆水域：只有在标准化交付和售后能力形成后进入。

不预先给出缺乏底稿的全国市场规模。任何 TAM、SAM、SOM 必须附计算表、来源和假设。

## 10. 团队与执行体系

### 10.1 必备角色

| 角色 | 责任 | 不能由谁兼任的边界 |
| --- | --- | --- |
| 项目负责人 | 方向、资源、对外承诺和最终验收 | 不能同时充当唯一测试人 |
| Agent 与后端负责人 | Runtime、策略、工具、数据和 API | 不能自行批准自己提交的高风险策略 |
| 感知负责人 | 数据、标注、评测、模型和边缘部署 | 不能只报告有利于结论的指标 |
| 硬件负责人 | 船体、机构、电气、安全和现场测试 | 不能由软件人员替代安全结论 |
| 产品与运营负责人 | 用户流程、试点、成本、需求和反馈 | 不能只做 PPT，不做真实访谈 |
| 前端负责人 | 业务控制台、实时状态和可访问性 | 不能展示后端不存在的状态 |
| 测试与质量负责人 | 独立验证、证据保存和回归门禁 | 不能只执行 happy path |
| 指导教师或行业顾问 | 技术审核、资源连接和场景指导 | 不能替代团队完成项目主体 |

### 10.2 协作规则

- 每个工作包必须有负责人、输入、输出、截止时间和验收命令。
- 每个数字有唯一来源。
- 每个 API 有契约和调用方。
- 每个 Agent 工具有 Schema、权限和失败测试。
- 每个高风险动作有审计和审批策略。
- 任何“完成”必须附带可复现证据。
- 不并行修改同一文件的相邻区域；共享接口先冻结，再分派。

## 11. 风险清单

| 风险 | 概率 | 影响 | 预防 | 触发后的应对 |
| --- | --- | --- | --- | --- |
| Agent 做成表演层 | 高 | 高 | 先落 Run、Step、Tool、Policy | 暂停前端扩展，回到 Runtime |
| 现场数据和硬件延误 | 高 | 高 | 同步推进准真实测试 | 主动标注 E2，改讲软件闭环 |
| 真实海况误报 | 高 | 高 | 固定约束、时序校验、负样本 | 聚焦泡沫和白天平潮 |
| MQTT 或网络不稳定 | 中 | 高 | 幂等、PEL、补派、本地队列 | 现场使用本地 Broker 和故障演示 |
| 成本估算失真 | 高 | 中 | 供应商询价和敏感性分析 | 降级为区间，不给单点承诺 |
| 政府预算周期长 | 高 | 高 | 先做小额试点和效果付费 | 调整里程碑，不以签约时间绑技术 |
| 知识产权被抢 | 中 | 中 | 软著、专利、数据授权和保密协议 | 保留时间戳与研发记录 |
| 比赛材料过度包装 | 中 | 极高 | 证据分级和统一术语 | 立即撤回并修正全部材料 |
| 团队成员流失 | 中 | 高 | 文档化、角色备份、代码可持续 | 启动替代负责人 |

## 12. 比赛答辩设计

### 12.1 八分钟演示结构

1. 30 秒：一个真实乡镇治理场景和当前痛点。
2. 60 秒：系统不是卖船，而是解决发现、派单、执行和核算。
3. 150 秒：现场触发事件，Agent 展示计划、工具调用、派单和轨迹。
4. 90 秒：展示误报复核、无机器人、审批拒绝和恢复能力。
5. 90 秒：展示治理报表、单位成本和证据链。
6. 60 秒：用户、试点路径和商业假设。
7. 60 秒：团队、壁垒、风险和下一步。

### 12.2 必须准备的证据附件

- 用户访谈纪要和现场照片。
- 数据授权、隐私和影像使用说明。
- 数据集 manifest、标注规范和独立测试结果。
- 测试命令与原始输出。
- 模拟器配置、场景和统计口径。
- Agent 运行轨迹、失败样本和评测报告。
- 硬件 BOM、供应商询价和实物照片。
- 试点协议、意向书、会议纪要或反馈记录。
- 软著、专利和开源许可证清单。
- 成本模型、计算表和敏感性分析。

### 12.3 不能依赖的答辩方式

- 只播放预录视频。
- 用无数据源的图表支撑结论。
- 所有操作都由演示者手工触发，Agent 没有自主轨迹。
- 评委追问后无法指出代码、接口、测试或数据位置。
- 网络断开后主链路完全不可演示。

## 13. DeepSeek Harness 分工开发方案

### 13.1 分派原则

DeepSeek Harness 不直接获得“把项目做好”这种模糊目标。每个工作包必须以文件边界、接口契约、验收命令和禁止事项为约束。共享接口先由总控冻结，再并行开发。

建议初始化 Git 仓库，主分支保存稳定基线。工作包之间按数据模型、Agent 内核、API、前端、评测、感知、商业文档六个边界拆分。共享文件如路由注册、模型导出、依赖文件由集成负责人统一修改。

### 13.2 工作包

| 工作包 | 范围 | 主要文件 | 验收 |
| --- | --- | --- | --- |
| WP-00 基线修复 | Pillow、编码、全量测试、版本控制 | 测试环境、脚本、README | 335 项测试完整执行，结果可复现 |
| WP-01 Agent 内核 | Runtime、Run、Step、Tool、Policy、Memory | `backend/app/services/agents/` | 六类失败场景测试通过 |
| WP-02 数据与迁移 | ORM、SQL、Alembic | 模型、迁移和初始化脚本 | 新库可建，旧库可迁移 |
| WP-03 API 与权限 | 运行、步骤、审批、工具和评测 API | API router、Schema、deps | 契约、权限和审计测试通过 |
| WP-04 前端控制台 | 运行、轨迹、审批、回放 | `AgentsView.vue`、API 客户端 | 真状态、空状态、失败状态和移动端可用 |
| WP-05 评测系统 | 场景集、指标、回归和报告 | `backend/tests/agent_evals/`、脚本 | 固定场景可一键执行并输出 JSON |
| WP-06 感知评测 | 数据集 manifest、OpenCV 评测、指标 API | `ml/`、`edge/` | 训练、验证和测试隔离，指标可复现 |
| WP-07 数据完整性 | coverage_area、闭环质量、报表口径 | report、stats、schema | 每项指标可追溯 |
| WP-08 商业与材料 | 访谈、询价、成本、证据附件 | `docs/business-model.md`、项目文档 | 数字有来源，未成交项明确标注 |
| WP-09 集成验收 | 契约、回归、演示和故障演练 | 跨模块集成 | 主链路、降级链路和证据包完整 |

### 13.3 工作包交付格式

每个工作包返回：

```text
状态：完成 / 部分完成 / 阻塞
修改文件：
实现内容：
关键设计：
执行的测试：
测试结果：
未完成事项：
风险与假设：
需要总控决策：
```

没有测试结果、文件清单和边界说明的输出，不视为完成。

### 13.4 并行边界

可以并行：

- Agent 内核与前端视觉框架。
- 数据库迁移与评测场景设计。
- 感知评测与商业材料。
- 数据完整性与答辩素材。

不能并行冲突：

- 多个工作包同时修改路由注册文件。
- 多个工作包同时修改根依赖文件。
- 多个工作包同时定义 Agent 状态枚举。
- 未冻结 API Schema 前开发消费该 API 的前端。

## 14. 总体验收标准

### 14.1 工程

- 完整测试通过，结果与文档一致。
- Agent Runtime 不依赖外部大模型即可运行。
- 所有工具调用有 Schema、权限、超时、幂等和审计。
- 成功、失败、取消、审批拒绝和超时都有轨迹。
- 关键数据库迁移可重复执行。

### 14.2 产品

- 用户能从告警走到任务完成和报表。
- 用户能看懂 Agent 做了什么、为什么做、何时需要介入。
- 无机器人、工具故障和网络异常时有明确状态。
- 不支持的能力在界面上显示为不可用，不伪造状态。

### 14.3 数据与模型

- 数据集有授权、版本和 manifest。
- 训练、验证、独立测试不泄漏。
- 指标有分母、样本量、分层和置信区间。
- 合成数据、准真实数据和真实数据严格区分。

### 14.4 商业

- 每个商业数字有来源级别和更新日期。
- 访谈、询价、意向、协议和验收分别归档。
- 至少验证一个用户的流程和付费意愿。
- 明确“试点验证”和“商业成交”的边界。

### 14.5 比赛

- 八分钟内主链路可现场运行。
- 评委可以随机追问技术、数据、成本和风险。
- 每个关键结论都能指向代码、测试、数据或附件。
- 项目在创新、技术、产品、商业和团队五个维度口径一致。

## 15. 立即执行顺序

1. 修复测试环境和 Windows 编码，取得全绿基线。
2. 初始化 Git，保存基线提交。
3. 本计划书作为统一口径，同步修订 README、架构、软件设计和产品分析中的过期数字。
4. 先实现 Agent Runtime 最小闭环，再扩展前端和评测。
5. 用 DeepSeek Harness 按工作包并行开发，由总控负责接口冻结、集成和验收。
6. 每周至少完成一次真实证据更新；没有新证据的功能不计入比赛进度。

本计划书不能代替真实订单、真实数据、真实硬件和现场测试。它的价值在于把团队的工作从“堆功能”约束到“形成可以经受评委、用户和工程验证的证据链”。只要这条证据链成立，项目才具备真正稳定的国奖候选力。
