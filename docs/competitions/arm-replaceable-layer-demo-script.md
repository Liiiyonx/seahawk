# 机械臂演示：90 秒可替换层脚本

> 用途：答辩现场照着念 + 照着做。目标是让评委亲眼看到「换执行端，平台不动」。
> 配套代码：`edge/arm_bridge/drivers.py`（ArmDriver 协议 + 注册表）、
> `frontend/src/components/ArmSimConsole.vue`（执行后端面板）。

## 为什么演示「可替换层」而不是演示机械臂

机械臂动作本身评委看不出技术含量——**同一套派单操作在两个执行端上跑出完全一致的结果**，才是我们平台的差异点。所以脚本的编排逻辑是：先让评委看"平台怎么派单"，再证明"换执行端平台无感"。

口径纪律（现场必须守住）：

- 机械臂台是**厂商控制环境**，是观测窗，不是我们平台的能力。
- 现场连线 = **E2 受控实验**，不说"现场验证""已部署"。
- 逆运动学源码未从树莓派取回前，不说"坐标级抓取"；GPS 目标只是任务上下文，
  不是关节角。
- 幻尔示教序列是**预示教舵机位置（0..1000）**，不是坐标。这是"能做会说不做"
  与"能做说不准"的分界线，别在这一点上说错。

## 已注册的三种执行端

| `driver.backend` | 性质 | 用途 |
|---|---|---|
| `simulated` | 仿真 | dry-run 验证平台协议闭环，不驱动硬件 |
| `http` | 转接口 | 把指令转发到 HTTP 端点，对接第三方机械臂 |
| `hiwonder_bus_servo` | **真机** | 树莓派总线舵机，按示教序列动作 |

三者的 MQTT 契约完全一致：`task` / `ack` / `progress` / `telemetry`。
切换只改 `config.yaml` 的 `driver.backend` 一个字段，或启动时
`--driver <name>` 覆盖。

## 90 秒脚本

### 第 1 段 · 仿真态跑通全链路（约 30 秒）

启动桥接层（仿真后端）：

```bash
python edge/arm_bridge/main.py --driver simulated
```

在平台大屏派一张单。评委看工单状态机走完：

```
pending → assigned → navigating → collecting → done
```

> 话术：「这是仿真执行器。刚才这一轮验证的是**平台的协议闭环**——
> 派单、确认、进度回传、证据落库，全部由平台完成，
> 执行端只是这次恰好不接真实硬件。」

### 第 2 段 · 换执行端（约 10 秒，不改平台任何代码）

当着评委面改后端。**推荐用命令行覆盖，比改文件更直观**：

```bash
python edge/arm_bridge/main.py --driver hiwonder_bus_servo
```

> 话术：「换执行端。**平台和桥接层一行代码没动**——
> 执行端是一个可替换层，配置文件一个字段切换。」

（若要展示配置文件驱动，可提前备好两份 config：切 `driver.backend` 后重启。
但命令行 `--driver` 更稳，不会因为改错文件当场起不来。）

### 第 3 段 · 真机态跑同一套操作（约 35 秒）

在平台派**同一类**工单。机械臂按示教序列动作，`progress` 实时回传，工单转 `done`。

同时打开机械臂台窗口（ArmPiFPV 上位机 / NoMachine Web），让评委看到上位机里的
真实动作 —— 这是「厂商仿真台在这里只是真机执行状态的观测窗，不参与平台闭环」
这句话的实证。

### 第 4 段 · 点睛：报文对比（约 15 秒，最高价值）

把两轮的 MQTT 报文并排放：

```bash
# 先起一个订阅，再在平台派两轮单（一轮 simulated，一轮 hiwonder）
mosquitto_sub -h <broker> -t 'seahawk/arm/#' -v > /tmp/arm-compare.log
```

> 话术：「这两轮的报文**逐字段一致**，只有执行端不同。
> 这意味着今天接的是幻尔教育臂，明天换成工业清理机械臂，
> 平台的派单逻辑、状态机、证据链**全部零改动**。」

**这是全场最硬的一块证据，比任何架构图都有说服力。** 建议提前录屏存档：
现场 broker 或网络出问题时直接切录屏，口径不变，仍是 E2。

## 页面上要能看见的（已实现）

`ArmSimConsole` 的「执行后端（可替换层）」面板直接显示：

- 三种执行端的名称，真机那款用主色标出，一眼能认出"哪个是真家伙"
- 当前 `driver.backend` 值
- 一行说明：三者共用同一份 MQTT 契约，切换只改一个字段

评委在界面上能读到"可替换"三个字落在实处，而不是只听你说。

## 现场网络：最大的坑，提前排

树莓派默认是 **AP 直连模式**（`192.168.149.1`），要求演示电脑单独连它的热点——
**这样电脑就上不了网、访问不了 ECS 上的平台**。必须提前处理：

| 方案 | 做法 | 适用 |
|---|---|---|
| **STA 模式（推荐）** | 树莓派改 STA 模式接入演示网路由器/热点，`VITE_ARM_CONSOLE_URL` 填它在演示网的 IP | 平台在 ECS（公网）+ 树莓派在本地，电脑只连一个网 |
| 双机方案 | 一台电脑连热点跑平台本地版（docker compose），另一台放仿真台 | 网络条件最差的兜底 |

演示前必查（在树莓派上执行）：

```bash
# 确认已切 STA 模式且拿到演示网 IP
ip addr show wlan0 | grep 'inet '

# 确认 NoMachine 已在跑（社区版是否开放 web player 待到货验证）
systemctl status nomachine
ss -tlnp | grep 4080
```

平台侧的可达性预检已内建：`ArmSimConsole` 会在挂载时和每 30 秒探测一次，
不可达时按钮下方直接给出排障指引，把"现场翻车"变成"现场排障"。

## 跳转方式（三档，配同一个键）

`VITE_ARM_CONSOLE_URL` 一个键覆盖三档，组件按协议自动判断：

| 档 | 填什么 | 体验 | 前提 |
|---|---|---|---|
| C | `http://<IP>:<port>`（ArmPiFPV Web 上位机） | 最佳，原生 Web | 到货后在 `/home/ubuntu` 下确认有没有 Web 上位机 |
| A | `http://<IP>:4080`（NoMachine Web Player） | 浏览器直连树莓派桌面 | 社区版 8.4 是否开放 web player 待验证 |
| B | `nx://<IP>` | 唤起本机 NoMachine 客户端，流畅度最高 | 演示机预装客户端（资料包有 `nomachine_8.4.2_10_x64.exe`） |

**到货后按 C → A → B 顺序探测，谁通用谁。**
