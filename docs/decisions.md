# 关键技术决策记录（ADR）

> 记录**为什么这么选**，而不是选了什么 —— 后者看代码就知道，
> 前者三个月后连自己都会忘，答辩时却最容易被追问。

格式：每条决策写清【背景】【选项】【决定】【理由】【代价】。
代价一栏不能省 —— 只写优点的决策记录是宣传，不是记录。

## ADR-001 平台的核心表是事件表与工单表，不是视频表

**背景**：项目名字里有"视频实时检测"，最直觉的做法是围绕视频流建表（存录像片段、按视频检索）。

**选项**
- A：以视频为中心 —— 存录像、标注关键帧、按视频组织数据
- B：以事件为中心 —— 检测结果落成结构化事件，视频只作证据链附件

**决定**：选 B。

**理由**：这个系统的用户是渔港管理部门，他们要回答的是
"哪个海域、哪类垃圾、多少量、处理了没有"，
而不是"第 37 分钟第 5 秒那个画面里有什么"。
视频是**证据**，事件才是**业务对象**。围绕视频建表，
后续所有统计（热力图、趋势、报表）都要先解码视频，成本极高且难做权限控制。

**代价**：需要额外做一套"事件落库 + 视频片段截取关联"，比纯存录像复杂。
但这是**一次性的复杂度**，而围绕视频建表是**持续性的复杂度**。

## ADR-002 视频流不经过边缘盒

**背景**：边缘盒既要跑推理，又要负责把视频转发给前端大屏。

**选项**
- A：摄像头 → 边缘盒 → （转发给）前端 + （本地推理）
- B：摄像头 → 流媒体服务器 → 前端，边缘盒**旁路取流**只做推理

**决定**：选 B。用 go2rtc 做流媒体中转，前端直接连流媒体服务器。

**理由**：边缘盒（RK3588 这类）的算力是**稀缺资源**，而转发视频是纯 I/O 开销。
让边缘盒兼做转发，等于让推理和转发抢同一块算力和内存带宽 ——
一旦前端看的人多了，推理帧率就被拖垮，而推理才是这套系统的价值所在。
旁路取流后，边缘盒只负责"看"和"上报"，转发压力交给专门的流媒体服务。

**代价**：多一个 go2rtc 服务要部署运维；网络路径变长一跳
（但这个跳转发生在局域网/内网，延迟可忽略）。

## ADR-003 用抽帧推理压制误报，而不是加严置信度阈值

**背景**：海面反光、浪花泡沫会被模型误判为"泡沫类垃圾"。
第一版每帧都推理，误报率很高，抑制率只有 ~20%。

**选项**
- A：提高置信度阈值（如 0.5 → 0.8）
- B：加时序校验（连续 N 帧命中才确认）
- C：抽帧推理（每 N 帧推一次）+ 时序校验
- D：换个更大的模型

**决定**：选 C（抽帧 `decimation=4` + 15 帧窗口时序校验）。

**理由**：
- A 的问题是**误报和漏报同时恶化** —— 阈值提上去，真实但模糊的目标也被滤掉了。
- B 单独用不够：浪花可以连续多帧存在，纯时序会把它确认为真。
- D 不可行：边缘盒算力固定，大模型跑不动。
- C 的关键在于**抽帧天然压噪声**：单帧闪现的浪花被抽中的概率只有 1/N。
  这不是"碰巧"，而是采样定理的直接后果 —— 高频噪声在低频采样下会被严重压制。

**代价**：确认延迟变长（需要 15 帧窗口，在 8fps 下约 2 秒）。
对海漂垃圾场景可接受 —— 垃圾不会 2 秒内漂走。

**实测**：抑制率 41.9% ~ 43.0%（三个场景），且 `fed = absorbed + suppressed` 恒成立。

## ADR-004 抑制率统计必须同单位计数

**背景**：第一版统计出"抑制率 140.9%"，明显荒谬（比率不可能 >100%）。

**根因**：分子用「淘汰的 track 数」，分母用「输入检测数」——
**两个不同的东西做除法**。一个 track 可能吸收了多条检测，
于是分子反而比分母大。

**决定**：统一为三个**同单位**计数：
- `fed`：输入给校验器的检测数
- `absorbed`：被确认为真、进入事件的检测数
- `suppressed`：被压掉的检测数

不变量：`fed == absorbed + suppressed`，且 `suppressed / fed ∈ [0, 1]`。

**代价**：需要多维护一个计数器。但换来的是比率**恒在合法区间**，
并且这个不变量本身可以写成断言当守门测试 —— 任何统计口径错误都会立刻暴露。

**教训**：比率类指标出现越界（>100% 或负数）时，
第一反应不该是"阈值调参"，而是**检查分子分母是不是同一种东西**。

## ADR-005 任何单一依赖缺失都不阻断启动

**背景**：演示现场或队友本地往往没有完整基础设施（无 Redis、无 MQTT Broker）。

**决定**：Redis / MQTT / 数据库 / 模型文件 / passlib 全部可降级，
缺失时打 WARNING 并继续启动，只让**依赖该能力的功能**不可用。

**具体做法**：所有可能失败的 import 都放进 `try` 块**内部**
（写在 `try` 外面等于宣称能降级但实际会崩在 import 阶段）；
关闭路径逐项 try，并对可能为 `None` 的对象加守卫。

**代价**：故障变得"安静" —— 服务起来了但某功能不可用。
因此必须有配套的**健康检查如实反映降级状态**（见 ADR-006）。

## ADR-006 `/health` 必须反映真实降级，且分三档

**背景**：早期实现无条件返回 `{"status": "ok"}`，即使所有依赖全挂。

**为什么危险**：编排系统（compose healthcheck / K8s probe）依赖它。
永远返回 ok 意味着**故障不会被重启、不会被告警，被静默吞掉** ——
比"服务挂了"严重得多，因为挂了至少有信号。

**决定**：逐项探测 `redis` / `mqtt` / `database`（各带 2 秒超时），
按最差项给出三档状态，并在 `dependencies` 字段列出明细：

| 状态 | 触发条件 | 编排系统应有的反应 |
| --- | --- | --- |
| `ok` | 全部依赖正常 | 不做处理 |
| `degraded` | 部分不可用（只读接口仍可用） | 告警，但**不要**重启 |
| `down` | 核心依赖全部不可用 | 可重启 |

**刻意不做的事**：不把原始异常消息放进响应体。
`/health` 通常免认证，而异常文本可能带连接串、主机名、账号。
只返回异常**类型名**（如 `down: TimeoutError`）已足够定位方向。

**代价**：健康检查有最多 3×2=6 秒的耗时。可接受。

## ADR-007 schema 管理采用「双轨制」

**背景**：初始 schema 里有三样 Alembic 表达不了或很别扭的东西：
`CREATE EXTENSION postgis`、`t_track` 按月分区表（`PARTITION OF`）、触发器函数。

**选项**
- A：全部用 Alembic，用 `op.execute("原生SQL")` 硬塞
- B：全部用 SQL 脚本，不用迁移工具
- C：双轨 —— 初始建表走 SQL 脚本，后续增量走 Alembic

**决定**：选 C。

**理由**：A 会让初始迁移变成一大坨原生 SQL，**失去 autogenerate 的价值**
（而 autogenerate 正是用 Alembic 的主要理由），还多一层间接。
B 的问题是后续加个字段都要手写 SQL 且没有版本追踪，团队协作必出乱子。

**代价**：两轨必须**人工对齐**（新环境要执行一次 `alembic stamp head`），
漏了会导致 autogenerate 生成一堆 `create_table` 然后执行报"表已存在"。
这个代价通过**在部署文档里把三步写成硬流程**来兜住。

## ADR-008 Alembic 主配置放在 pyproject.toml，而非 alembic.ini

**背景**：`alembic` 的所有子命令在中文 Windows 上崩溃：
`UnicodeDecodeError: 'gbk' codec can't decode byte 0x80`。

**根因**：Alembic 读 ini 时硬编码 `encoding="locale"`
（`alembic/util/compat.py:130`），而 `open(encoding="locale")`
取的是 `locale.getencoding()` = **cp936(GBK)**，**绕过 UTF-8 模式**。
于是 ini 里出现任何非 ASCII 字节（哪怕只是中文注释）就崩。

**试过但无效**：加 `# -*- coding: utf-8 -*-`（显式传 encoding 时该声明被忽略）、
设 `PYTHONUTF8=1`（管不住 `encoding="locale"`）。

**决定**：主配置迁到 `pyproject.toml`。Alembic 读 TOML 用
`open(path, "rb")` + `tomllib` —— 二进制模式，编码参数根本不参与，根治。
`alembic.ini` 只保留日志段（TOML 不支持 configparser 的 `[loggers]` 结构），
且**必须保持纯 ASCII**。

**代价**：两个配置文件，且 TOML 写法与 ini 有两处不同
（`file_template` 仍需双百分号；`version_locations` 必须是**数组**，
写成字符串会被逐字符遍历并报出极具误导性的 `Empty module name`）。
代价已通过文件内注释 + 部署文档详述来兜住。

## ADR-009 前端绝不直连 MQTT

**背景**：设备状态需要实时刷新，最直接的做法是前端连 MQTT 订阅。

**决定**：前端只通过 HTTP 拉取 + WebSocket 接收后端推送，**不碰 MQTT**。

**理由**：
1. **安全**：前端连 MQTT 就必须把 broker 地址和凭据下发到浏览器 ——
   等于公开发布。ACL 最小权限也防不住"合法用户拿凭据伪造上报"。
2. **一致性**：多个前端各自订阅会各自做一遍解析与聚合，
   口径容易漂移（比如"在线设备"的判定逻辑），后端统一处理后推送才可控。
3. **可替换**：后端内部换消息中间件时，前端完全无感。

**代价**：后端要维护 WebSocket 连接管理（心跳、断线重连、广播）。
已在 `app/ws/manager.py` 实现。

## ADR-010 边缘端 seq 必须持久化

**背景**：平台用 `(device_id, seq)` 唯一约束做幂等去重。

**决定**：边缘端（含模拟器）的 seq 必须**单调递增且落盘持久化**，
崩溃重启后从上次值续上。

**理由**：若重启后 seq 归零，第一条事件 seq=1 与平台已有记录冲突，
平台判为重复 → **后续所有事件都被静默吞掉，且没有任何报错**。
这是演示现场最容易翻车的点：程序"正常运行"、日志"正常上报"、就是不出数据。

**代价**：多一个状态文件。注意该文件**绝不能提交到仓库**
（否则别人 clone 会带着你的 seq 续跑，两台机器 seq 撞车）——
已在 `.gitignore` 排除。

## ADR-011 预处理用 letterbox，不用直接 resize

**背景**：推理服务要把任意分辨率的原图缩到 640×640。两种做法：
直接拉伸（快，但宽高比失真）、等比缩放 + 灰边填充（letterbox，符合训练分布）。

**选项**：
- A 直接 `resize((640, 640))` —— 三行代码
- B letterbox：等比缩放，短边补 114 灰边到 640
- C 改成 640×360 之类贴合 16:9 的输入尺寸，从根上避免 padding

**决定**：选 **B**。

**理由**：
1. **训练端就是这么做的**。Ultralytics 训练时默认 letterbox，推理端不一致
   会让框的位置与形状系统性偏移，越靠画面边缘越明显。
2. **A 的问题不会立刻暴露**。项目长期走 stub 模式（无真实模型），
   直接 resize 也能"跑通"，直到真模型挂上去才发现框画偏 ——
   而此时很容易误判成"模型不准"，去调训练参数，方向完全错了。
3. **C 不可行**：采集来的图不止一种宽高比（岸基 16:9、无人机 4:3、
   手机竖拍 9:16），固定成某一个比例总有一批图要变形。

**代价**：
- 多一些计算与代码（`_letterbox` 返回 scale 与 pad，后处理必须用上）。
- **填充色必须与训练端一致（114 灰）**：换成纯黑会让模型在图像边界
  看到训练时没见过的分布，边缘目标置信度莫名偏低。这个约束写在
  代码注释与测试 `test_padding_colour_is_114_grey` 里。
- 还原时要先减 pad 再除 scale，顺序错或漏 pad，框会整体平移。
  已在两条解析路径上分别写了断言。

## ADR-012 算法参数以设计文档为唯一真源，并由测试强制对齐

**背景**：`max_misses` 出现了三方不一致 —— 设计文档写 **5**、
代码默认值写 **6**、单元测试里也硬写 **6**。功能上完全正常，
没有任何报错，因此长期无人发现。

**选项**：
- A 手工同步：改代码时记得去改文档
- B 把参数只放一处（config.yaml），代码与文档都引用它
- C 文档作真源，**加测试断言**核对代码默认值与文档参数表

**决定**：选 **C**（其中 config.yaml 作为运行时可覆盖层，见下）。

**理由**：
1. **A 已经证明不可靠** —— 它不是"可能忘"，而是"已经忘了且没被发现"。
2. **B 对本项目不适用**：设计文档是要交给外部评审看的独立交付物，
   它必须能自证参数取值，不能写成"见 config.yaml"。
3. **C 把不一致变成可检出**。测试不再复述那个数字（复述等于没测），
   而是从 `inspect.signature` 读取实现默认值，再与文档参数表正则比对。
   文档与代码各说各话从"隐形缺陷"变成"一条会失败的断言"。

**代价**：
- 文档参数表的格式不能随便改（`| \`param\` | 值 |` 的表格结构被正则依赖）。
  改格式要先改测试。
- 数值写法要规范：带单位的写法（如 `60 px`）已做兼容，但
  写成"约 60"或"<60"这种就匹配不到了，会直接测试失败 —— 这是有意的，
  参数表要能被机器读。
- 同一轮还暴露了配套缺陷：`match_distance` 与 `min_iou`
  **在实例化校验器时被漏传**，只能靠类默认值兜着，意味着在
  `config.yaml` 里改了不生效且不报错。已补齐注入链，
  并加 `test_config_yaml_declares_all_thresholds` 断言配置键齐全。

## ADR-013 MQTT 消息路由的判据必须用「结构」，不能用「总段数」

**背景**：`robot/{robot_id}/cmd/ack` 的路由分支写成 `len(parts) == 5`
再比对第 3/4 段。但通配符 `robot/+/cmd/ack` 展开后**只有 4 段**，
该条件永远不成立。而它前面的 `elif len(parts) == 4 and parts[0] == "robot"`
分支只识别 `parts[3] == "progress"`，`ack` 直接落到 `return None`。

后果：机器人回 ACK → 平台收不到 → 任务永远停在 `assigned`，
无法进入 `navigating`。**整条作业链路从第一步就断。**

最恶劣的地方在于：`handle_robot_ack` 本身实现得好好的，
它的单元测试全绿 —— 因为那个函数**永远不会被调用**。
没有异常、没有日志、没有告警，大屏上只表现为「派了单机器人不出发」。

**选项**：
- A 改成 `len(parts) == 4`（即只修那个错误的数字）
- B 按「结构」逐段比对：第 1 段是 `robot`、第 3/4 段是什么
- C 去掉通配符订阅，改为精确订阅每台机器人的主题（设备数固定时可行）

**决定**：选 **B**。

**理由**：
1. **A 治不了根**。`robot/{id}/task/progress` 与 `robot/{id}/cmd/ack`
   **段数完全相同（都是 4）**，所以段数天然无法区分这两条路径。
   只把 5 改成 4，会让两条主题互相短路 —— 从「收不到」变成
   「收到了但认错人」，更难排查。**用长度做判据这件事本身就是错的。**
2. **B 让判据与主题树的语义对齐**。判据表达的是"第 n 段应该是什么"，
   这正是主题设计的本意；加新主题时也不会因为段数巧合而互相干扰。
3. **C 会牺牲可扩展性**，且设备动态上下线时要重订阅，把简单问题复杂化。

**代价**：
- `_match_handler` 的写法比"数段数"啰嗦一些，需逐段列出。
  已在 docstring 里写明为什么不能用长度，防止后人"优化"回去。
- 新增了一条守卫测试 `test_robot_topics_have_same_segment_count`，
  它不断言业务行为，而是**锁住根因**：只要 robot 族主题仍然同段数，
  任何人想退回长度判据都会立刻踩红。
- 同轮发现的姊妹缺陷：`handle_robot_progress` 的状态映射表漏了 `done`。
  两者同属「文档声明了某集合、代码只实现了一部分」，见 ADR-014。

## ADR-014 凡「文档声明了某集合」的地方，都要有穷举式守卫

**背景**：同一轮审查里发现四个缺陷，它们的形状完全一致：

| # | 文档声明 | 代码实现 | 表现 |
| --- | --- | --- | --- |
| 1 | 平台订阅 5 条主题 | 路由表覆盖 4 条 | ACK 被静默丢弃 |
| 2 | §5.6 声明 4 种作业状态 | 映射表只有 3 种 | 任务卡在 collecting |
| 3 | 契约声明类别为 enum | schema 用裸 `str` | 非法类别一路放行 |
| 4 | 派单白名单是单一规则 | MQTT/HTTP 两侧各写一份 | 两入口行为不一致 |

它们的共同点：**不报错、不抛异常、也不打日志**。
第二个缺陷尤其典型 —— `dict.get("done")` 返回 `None`，
被 `if target and ...` 一口吞掉，整条闭环断在最后一步而无人知晓。

这类缺陷抽样测试抓不到：手写三条用例，很可能恰好抽到已实现的那三种状态。

**选项**：
- A 为上表每一处补几条单元测试（抽样）
- B 写一个检查脚本，从文档解析出"声明集合"，
  从代码解析出"实现集合"，**逐项比对**，差异即失败
- C 只在代码上加日志，靠人工巡检发现

**决定**：选 **B**，并在 Makefile 接入 `make check-contract`。

**理由**：
1. **A 不足以覆盖**。"文档声明 N 项、代码实现 N-1 项"这种缺陷，
   抽样的命中率是 1/N，且随着集合增大而下降。只有**集合比对**才能
   把"N 项对 N 项"变成一条确定性断言。
2. **B 可复用**。新增一种作业状态时，只要文档写了、代码没写，
   脚本立刻报红 —— 不需要有人记得去补测试。
3. **C 不可靠**。日志需要有人看；实测中这类问题是在做系统审查时
   通过读代码发现的，而不是日志报出来的。

**代价**：
- 检查脚本依赖**文档格式**（表格结构、反引号、箭头符号）。
  文档改格式会让脚本失效 —— 所以脚本在解析不到内容时**报 FAIL 而非静默通过**，
  且用"基线必须为绿 + 注入缺陷必须变红"的自证来保证它没空转。
- ★ 这里踩到一个更深的坑：**校验工具自身也会静默失效**。
  本轮就发生了四次 —— AST 遍历漏掉 `AsyncFunctionDef`、
  路由判据本身写错导致脚本自造假缺陷、把文档主题总表的
  「设备 → 平台」误读成「平台必须订阅」、自证脚本的注入锚点写错。
  故补 `scripts/selftest_contract_drift.py`：**注入 8 种已知历史缺陷，
  逐项确认检查脚本真的会红**，任何一项锚点失效或未被捕获即退出码非 0。
  一个永远返回全绿的检查脚本比没有脚本更糟，它给的是虚假的安全感。

## ADR-015 类别枚举在 schema 层用 `Literal` 收紧，不做运行时降级

**背景**：`EventAggregate.main_class` 与 `DetectionItem.class` 原为裸 `str`。
而该字段同时被三处消费：前端配色（查 `CLASS_ORDER`）、
派单白名单（`WasteClass.HIGH_PRIORITY`）、数据库 `waste_class_enum` 列。

放行一个非法类别的后果是**三处同时静默失效**：配色回退成灰、
派单条件不命中、入库被 DB 拒绝而整个事件丢失。

**选项**：
- A 放行任意字符串，在 handler 里遇到未知类别时记 warning 并降级
- B 在 schema 层用 `Literal["foam","plastic","fishing_gear","other"]` 硬约束
- C 用 `field_validator` 校验但返回一个默认值（如 `other`）

**决定**：选 **B**。

**理由**：
1. **A/C 都是"宽容"路线，但这里宽容没有收益**。设备上报的类别由
   模型输出决定，四类是封闭集合；出现第五类只可能是
   （a）模型改了但契约没同步 → 需要人介入，不该静默降级
   （b）报文损坏 → 更不该入库。
   把非法值降级成 `other` 会让缺陷伪装成正常数据，污染误报率统计。
2. **B 让契约自证**。用 `Literal` 而非 `field_validator`，
   FastAPI 生成的 OpenAPI 文档会自动带上 `enum` 约束 ——
   前端与设备方看接口文档就能知道取值域，不必另外维护一份说明。
3. **B 是失败快速的**。坏报文在入口被挡下并留下明确的校验错误，
   而不是流进业务层再以某种间接方式出错。

**代价**：
- 收紧后必须同步文档，否则边缘端实现者可能漏发。
  已补 `docs/mqtt-topics.md` 中 `aggregate` 对象本身的必填标记，
  并写明 `main_class` 的四个取值（原来只写"主要类别"，过于模糊）。
- **未来要给模型加第五类时，必须同时改四处**：`WasteClass.ALL`、
  DB 的 `waste_class_enum`、前端 `CLASS_ORDER`、以及 schema 的 `Literal`。
  为降低漏改风险，`check_contract_drift.py` 会把这几处逐一对账
  （含顺序敏感项 `CLASS_NAMES`，因为顺序即模型输出索引）。
- 有意保留一处例外：`EventIngest.device_type` 文档标必填但 schema 有默认值，
  这是为了让不带上报类型的老固件也能入库，handler 另有 `.get` 兜底。
  检查脚本对此只作提示、不计警告 —— 长期挂着的 WARN 会导致告警疲劳。

## ADR-016 手工拼装的推送负载必须由契约常量 + AST 穷举扫描守住

**背景**：WebSocket 推送负载是**手工拼的 dict**，散落在四处：
`mqtt/handlers.py`（2 处）、`api/v1/tasks.py`、`services/consumer.py`。

实测发现：同一份 `task_update` 契约（`api.md` 声明 data 含
`task_id`/`event_id`/`robot_id`/`status` 四个字段），
在 `handlers.handle_robot_progress` 那处**漏了 `event_id`**。

这个缺陷的隐蔽程度值得记下来：前端 `pushTask` 用 `{ ...data }` 展开，
缺字段静默变成 `undefined`。而当前前端只把 `taskFeed` 当
「有更新就重拉全量」的触发器，**不直接渲染其字段** ——
所以这个缺陷在界面上完全看不出来，界面上一切正常。

真正危险的是将来：一旦有人开始直接渲染 `taskFeed` 里的字段，
就会拿到 `undefined` 且不知道为什么。契约写了四个字段就得给四个。

同轮还发现 `tasks.py` 推的是完整 `TaskOut.model_dump()`（16 字段），
而 `handlers.py` 推的是**手工裁剪的子集** —— 两处形态不同，
手工裁剪的正是漏字段的根源。

**选项**：
- A 让所有推送点都推完整模型（`TaskOut.model_dump()`）
- B 把契约（消息类型 + 必带字段）提取为常量，
  并用 **AST 静态扫描**穷举所有推送调用点逐个校验
- C 只在 `broadcast()` 里做运行期校验，缺字段就记 warning

**决定**：选 **B + C 的组合**（B 为主，C 作为兜底留痕）。

**理由**：
1. **A 不可行**。`handlers.py` 里的推送发生在 MQTT 上下文中，
   手里只有 task 对象、没有会话上下文去拼完整 `TaskOut`；
   而且大屏只需要少量字段，推全量是浪费。形态差异是合理的，
   问题在于**没有东西保证子集包含契约要求的字段**。
2. **B 是唯一能"穷举"的办法**。手工拼装必然漂移，靠人记得同步不现实。
   把契约变成常量后，用 AST 扫出每一处 push 调用的字面量 dict，
   逐个比对键集合 —— 新增推送点会被**自动纳入**检查，
   不需要有人记得来补测试。
3. **C 保留作为运行期兜底**。测试可能覆盖不到动态构造的负载，
   运行期 warning 能留下痕迹。**不阻断推送** ——
   大屏少一个字段也好过整条消息不发，但必须留痕。

**代价**：
- `WS_MESSAGE_CONTRACT` 与文档 `api.md` 的表必须同步。
  已加断言：契约里声明的类型集合与文档声明的 6 种**双向相等**，
  且各类型的字段数量不低于文档列出的个数。
- AST 扫描只对**字面量 dict** 有效；走 `model_dump()` 的推送
  单独用一条测试校验「模型字段覆盖契约要求」。
- 为此写了 `test_ws_contract.py`（18 项），并把 WS 层也纳入
  自证脚本 —— **脚本型守卫与测试型守卫都要自证**。
  已注入 4 项 WS 缺陷（漏字段 / 漏声明类型 / 契约少字段 /
  前端丢分支），全部被捕获。
- 又踩到一次「工具失真」：探针只看响应顶层字段，
  而业务字段都包在统一信封 `ApiResponse`（`code`/`data`/`message`/`trace_id`）里，
  于是**全部误报"缺失"**。教训：探针报"缺失/为空"时先自证工具可信。

## ADR-017 「本次调用的产物」必须由函数回传，绝不事后反查

**背景**：`POST /events` 的响应体里有 `task_created` / `task_id`
两个字段（`api.md:146-152` 声明），语义是「本次事件是否派单成功、派给了哪个任务」。

实际实现曾经这样写（`api/v1/events.py`）：

```python
await _try_dispatch(payload.event_id)
tasks = await TaskRepository(session).list_tasks(limit=1)
if tasks[0]:
    result.task_created = True
    result.task_id = tasks[0][0].task_id
```

这里叠加了**两处**错误，任何一处单独看都不显眼：

1. `list_tasks` 的返回类型是 `tuple[list[Task], int]`，代码**没解包**。
   于是 `tasks[0]` 拿到的是 list 而非 total —— 非空 list 恒为真值，
   那个 `if` 形同虚设。
2. 用「查全库最新一条任务」冒充「本次调用创建的任务」。

**后果分两层，第二层远比第一层危险**：

- 浅层：只要库里存在任意一条历史任务，`task_created` 就**恒为 True**。
  无可用机器人时接口照样回答「派单成功」，前端于是去轮询一个不存在的进度。
- 深层：并发上报时 `task_id` 指向的是**别人的**任务。前端拿它查
  `/tasks/{task_id}`，会看到一个与本次事件毫无关系的状态 ——
  而这个错误**在任何日志里都不会出现**。

**根因**不是「忘了解包」，是**把「本次调用的产物」当成了「可事后反查的东西」**。
这两件事看起来等价，实际上在并发下必然分叉。

**选项**：
- A 修正解包写法，仍从库里查（`tasks, total = ...`，再按 `event_id` 过滤）
- B 让 `_try_dispatch` 返回本次创建/命中的 `Task`，调用方直接用返回值
- C 让调用方自己构造 `task_id` 再传进去

**决定**：选 **B**。

**理由**：
1. **A 是治标**。「按 event_id 过滤」需要再猜一次「哪个任务对应本次事件」
   —— 而 `_try_dispatch` 内部**明明已经把这个 Task 拿在手里了**。
   让调用方绕一圈去数据库里重新找同一个对象，是在制造张冠李戴的机会。
   而且 A 还需要处理「过滤不到」的第三态，把问题复杂化。
2. **B 消除的是整类问题**，不只是这一处。`task_id` 是本次调用的**产物**，
   生产它的函数是唯一知道它的人，理应回传。这条规则一旦确立，
   将来新增任何「创建 X 并返回 X 的 id」的接口都不会再犯。
3. **C 行不通**：`task_id` 的生成依赖派单结果（可能合并到已有任务、
   可能无机器人可派），调用方无法预知。

**代价**：
- `_try_dispatch` 的签名从 `-> None` 变为 `-> Task | None`，
  **所有出口都必须显式 return**。漏一个裸 `return` 会使返回类型
  退化成 `NoneType`，调用方 `if task is not None` 永远为假 —— 又一个静默失效。
  为此加了 AST 穷举测试：遍历该函数**全部** `ast.Return` 节点，
  逐一断言非裸返回，且成功路径必须 `return task`。
- MQTT 路径的调用点忽略返回值（它不需要响应体），这没问题，
  但不能因此把签名改回去。已加测试断言签名含 `Task`。
- 新增 `test_events_ingest_contract.py`（12 项）+ `selftest_events_contract.py`
  （注入 4 种缺陷自证，全部命中）。

**这个形状会复现**，所以要写成通用守卫而非定点修补：
凡是「仓库方法返回 `tuple[...]` 却被赋给单个变量后又下标访问」的调用点，
一律由 AST 穷举扫描报出。当前全工程 `tuple[...]` 返回方法只有
`list_events` / `list_tasks` 两个，扫描器会随新方法自动扩展覆盖面。

## ADR-018 「优化类」逻辑必须由测试证明它真的在工作

**背景**：派单引擎的第五步「类别匹配加权」，文档
（`software-design.md:498`）的承诺是：

> ⑤ 类别加权     泡沫类任务顺路优先（减少空驶）

实现是这样的：

```python
def _class_match_weight(self, event: Event, task: Task) -> int:
    """类别匹配加权：0=匹配（更优），1=普通。

    同类别且在途的任务，说明机器人已在处理同类垃圾，
    复用可减少往返空驶。
    """
    return 0 if event.main_class == WasteClass.FOAM else 1
```

它收了 `task` 形参却**从未使用**。于是「同类别顺路优先」这句承诺
从未兑现：返回值只由本次事件的类别决定，对**同一个事件的
所有候选机器人完全相同** —— 排序实际只剩「距离」一维，
加权那一步是白算的。

这个缺陷的性质与之前几轮**不同**，值得单独立一条 ADR：

| | 前几轮的缺陷 | 本轮的缺陷 |
| --- | --- | --- |
| 系统行为 | 功能**坏掉**（消息丢弃、状态卡死、字段缺失） | 功能**变差**（少了一条优化） |
| 可观测性 | 至少能在数据里看出来 | 完全看不出来 |
| 严重性判据 | 契约 vs 实现 | **没有契约可比对** |

**关键难点：「优化失效」没有断言可写。** 端到端测试照样通过、
接口照样返回、日志照样打 INFO —— 系统只是"没那么聪明"了。
一个没有断言的优化，等同于不存在。

**选项**：
- A 补上两两比对，靠 code review 保证
- B 让加权函数**不接收**它不需要的参数（`event` only），
  并在文档里删掉「顺路复用」的承诺 —— 让文档与实现一致
- C 补上两两比对，并加**结构测试**：断言函数确实读取了两侧信息

**决定**：选 **C**（A 的修复 + B 的严格性，但拒绝删承诺）。

**理由**：
1. **B 是投降**。「顺路复用」是这个系统真实的价值点
   （减少往返空驶 = 省电 = 续航内多跑几趟），
   把它从文档里删掉等于承认这个功能不做。
2. **A 不够**。这类缺陷的特征就是**"看起来在工作"**——
   code review 时，函数有名字、有 docstring、有返回值、
   被正常调用，一切正常。审稿人很难注意到「形参没被用到」。
3. **C 的核心是找到可断言的替身**。既然「权重的值对不对」
   没有外部标准可依，就断言**结构**：
   - 形参必须被使用（AST 检查名字是否出现在函数体内）
   - 函数体必须同时引用「本次事件类别」与「在途任务类别」两侧
   - 行为上：同一事件配不同机器人状态，权重**必须不同**
     （旧实现恒相同 —— 这条断言直接钉死了退化）

**代价**：
- 「形参必须被使用」这个检查会误报**框架约定形参**
  （FastAPI 的 `lifespan(app)`、异常处理器的 `exc`、
  MQTT handler 的统一签名 `(topic, payload)`）。
  全工程扫出 4 处，全部是约定而非缺陷。
  处理方式是**显式允许清单**并写明理由，而不是关掉检查 ——
  允许清单里的名字一旦新增，review 时就能看到。
- 加权现在需要查「机器人手上的在途任务属于哪些事件」。
  必须**批量查**（`list_main_classes_for_events`），
  不能在候选循环里逐条查 —— 否则是 候选数 × 在途数 次查询。
- 顺带修掉同源的**第二处硬编码**：`priority = 1 if ... else 3`
  与 `WasteClass.HIGH_PRIORITY` 是两份策略副本。
  提取为 `TaskPriority`（单一真源，且内部引用 `HIGH_PRIORITY`），
  并用 AST 扫描禁止别处再出现 priority 三元式。
- 新增 `test_dispatch_engine.py`（14 项）+ `test_static_guards.py`（3 项）
  + `selftest_dispatch_contract.py`（注入 5 种缺陷，全部命中）。

**可复用的一句话**：**凡是没有断言的「优化」，都要假设它已经死了。**
用结构断言（形参是否被用、两侧是否都被读取）代替没有标准的值断言。

## ADR-019 多步流程必须收成「唯一出口」，不能各入口各写一遍

**日期**：2026-09-18
**状态**：已接受

### 背景

派单不是一个动作，是**三步**：

1. 在数据库里创建任务
2. 通过 MQTT 把指令下发给机器人
3. 通过 WebSocket 把新任务推给看板

本工程有**四个**派单入口，而实测只有两个走完了三步：

| 入口 | 建任务 | 下发 MQTT | 推送看板 |
| --- | --- | --- | --- |
| `handlers._try_dispatch`（HTTP 上报同步派单） | ✓ | ✓ | ✓ |
| `consumer._process_entry`（Streams 消费者） | ✓ | ✓ | ✓ |
| `consumer.pending_dispatcher`（定时补派） | ✓ | ✗ | ✗ |
| `dispatch.assign_pending_tasks`（补派 API） | ✓ | ✗ | ✗ |

后两个的后果：

- 数据库里**确实有**任务记录；
- 日志写着「本轮补派 N 个任务」；
- API 返回 `{"dispatched": N, "task_ids": [...]}` 且 HTTP 200；
- 而机器人**一条指令都没收到**，看板也不刷新，任务永远停在 `assigned`。

**全过程不报错、不抛异常、不打日志** —— 从外面看一切成功。

### ★ 这条缺陷与前面几轮的形状不同

- 前面几轮（ADR-014/016/017）是「**声明了 N 项、实现了 N-1 项**」；
- 本轮是「**实现了 N 步、只接上了 N-2 步**」。

代码本身没错，错在**没有接线**。而"没接线"是 grep 不出来的——
被调用的函数确实存在于源码里，`grep handle_ack_timeout` 也能搜到它。

### 选项

- **A**：在漏掉的两个入口里各补一遍下发 + 推送。
- **B**：把收尾动作收成 `finalize_dispatch(task)`，四个入口全部调用它。
- **C**：靠 code review 记住"派单要做三件事"。

### 决定

选 **B**，并用 AST 穷举守卫（而非逐个列举入口）保证它持续成立。

### 理由

- **A 只是把缺陷复制成四份**。下次新增第五个入口（比如定时任务、
  管理后台手动派单）时，仍然会漏，而且漏得一模一样。
- **C 不成立**。这条缺陷之所以活到现在，正是因为它"看起来完全正常"：
  日志说成功、API 说成功、数据库有记录。review 时没人会怀疑。
- **B 把「派单成功」这个词的定义固定在一处**。守卫不列举入口名，
  而是断言「凡是调了 `dispatch_for_event` 的地方，都必须调
  `finalize_dispatch`」——**新入口自动纳入覆盖面**，不需要有人记得更新清单。

### 代价

- `finalize_dispatch` 内部用局部 import（`mqtt_client` / `ws_manager`）
  避免循环导入，与工程既有风格一致但略显啰嗦。
- 穷举守卫依赖 AST 能找到调用点，所以守卫自身必须自证
  （`make check-finalize-selftest`）：必须扫到 ≥4 个入口，
  且必须包含曾经漏接的那两个——扫不到就判守卫失效，而不是判"没问题"。

### 附带修掉的同类问题

- **`handle_ack_timeout` 零调用点**：它是文档里「五步筛选」的第五步
  （ACK 超时换车重派），实现完整却从未被调用 —— 机器人掉线后任务
  永久停在 `assigned`，且因为**没有代码在跑**，连日志都不会有。
  现已在定时任务中接上，并新增 `reassign_task` 完成"回退 → 重派"闭环。
- **坐标取值绕道数据库**：历史写法 `select(ST_X(task.target_location))`
  没有 `where(...)`。实测该表达式是**字面量绑定**（无 FROM）所以语义正确，
  但这种正确性依赖读者知道 `task` 是实例而非类。一旦有人改成类引用，
  `.first()` 就会拿到**全表第一行**的坐标。故改为在内存里解析
  （`_parse_point`，支持 EWKT 与 EWKB），顺带省掉一次数据库往返。

## ADR-020 Redis Streams：不 ACK 就必须有人认领（PEL 回收）

**日期**：2026-09-18
**状态**：已接受

### 背景

`dispatch_consumer` 用 `xreadgroup(streams={stream: ">"})` 消费事件流。
而 `_process_entry` 在「无可用机器人」时刻意**不 ACK**，把消息留在
PEL（Pending Entries List）里等后续重试 —— 这个意图本身是对的。

但两者叠加后出了事：

- `">"` 的语义是**只读新消息**，PEL 里的条目**永远不会被返回**；
- 于是这些消息**永远不会被重投**（哪怕机器人后来上线了）；
- PEL 只增不减，且**不受 stream 的 `maxlen` 裁剪影响**；
- 功能上被 `pending_dispatcher` 从数据库兜住了，所以**从外面完全看不出来**。

结果：「留着重试」实际变成了「永久滞留 + 内存缓慢泄漏」。
不报错、不打日志，只能靠 `XPENDING` 才看得见。

### 决定

在主循环读新消息**之前**，先用 `xautoclaim` 认领挂起超过
`PEL_MIN_IDLE_MS`（60 秒）的条目，走一遍 `_process_entry`。

### 理由

- **一次改动同时解决两件事**：
  - 事件仍未派单且机器人已上线 → 正常派单并 ACK；
  - 事件已被定时补派处理掉 → 状态不是 NEW，直接 ACK，**PEL 随之清空**。
  也就是说，连"已被数据库补派、但 Redis 里那条一直没 ACK"的历史欠账
  都会被自然消化掉。
- `min_idle_ms` 必须 > 0。设成 0 会把「刚投递、正在处理」的消息也抢回来，
  同一条事件被并发处理两遍。已用测试钉住这个约束。

### 代价

- 要求 Redis ≥ 6.2（`xautoclaim`）。备赛与部署环境均满足。
- 每轮循环多一次 `xautoclaim` 调用（5 秒一次）。量级可忽略。
- 反复失败的消息会被无限重试（PEL 永不自动丢弃）。
  若将来需要"重试 N 次后进死信"，要在条目里记重试次数——当前由
  定时补派从数据库兜底，暂不需要。

### 缺陷形状归类

属于 ADR-019「实现了 N 步、只接上了 N-1 步」的近亲：
不是没人调用，而是**流程只写了一半** —— 有"不 ACK 留待重试"的意图，
却没有"谁去重试"的实现。这类缺陷同样 grep 不到，
必须靠「断言主循环调用了 `_reclaim_pending`」来钉住。
