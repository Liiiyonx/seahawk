【背景】
WP-14C 让平台真正消费冻结 ACK 信封；WP-14D 把判定落成 `t_task_ack` 审计账本，
提供 `TaskAckRepository.record_arrival` 与 `rebuild_ack_tracker`，并让
`handle_robot_ack` 走「校验与判定 → 写账本 → 状态推进 → 提交」单事务。
但截至 WP-14D 仍有三处未收口：
(1) `rebuild_ack_tracker` 只是能力方法，未接入应用启动流程，重启后判重水位不自动恢复；
(2) 设备孪生 `edge/device_sim` 的遥测 `seq` 只存在进程内存，重启后从头计数，
    平台侧看到的序号会倒退；
(3) 设备孪生到平台的 ACK 闭环没有一条可复现的端到端联调用例。

【目标】
把上面三处收口，使「设备孪生产生回执 → 平台消费 → 任务推进 → 落账本 →
进程重启 → 重复回执不再重复推进」成为一条可在本机无 Broker 条件下复现的闭环。

【实现要求】
1. 启动恢复接线：应用 lifespan 启动阶段在 MQTT 客户端可用后，尝试用
   `TaskAckRepository.rebuild_ack_tracker(mqtt_client.ack_tracker)` 从 `t_task_ack`
   恢复判重水位。必须做到：
   - 数据库不可用、表不存在或查询异常时**降级为 warning 并继续启动**，
     绝不让启动失败（与现有「每步独立 try」的降级风格一致）；
   - 恢复是幂等的，重复启动不叠加、不报错；
   - 恢复耗时要有上界（例如超时或行数上限），不得让启动无限期挂起；
   - 恢复结果（行数/耗时/是否降级）要能以可观测方式拿到（日志或健康检查字段），
     不得静默。
2. 设备孪生 `seq` 持久化：为 `edge/device_sim` 的遥测序号提供跨进程持久化：
   - 路径可配置（环境变量或构造参数），**默认不写盘**，保持现有测试与行为不变；
   - 落盘使用原子写（临时文件 + 替换），进程重启后序号严格单调递增，
     不得回退到 0 或重复已用序号；
   - 文件缺失或损坏时以 warning 降级（从 0 或最后一个可解析值开始），不得抛异常崩溃；
   - 必须覆盖「写盘 → 新进程重新加载 → New 号 > 旧号」的跨进程断言，
     且测试不得依赖真实网络。
3. 孪生闭环联调（不依赖真实 Broker）：写一条端到端用例，串起
   `edge/device_sim` 生成的冻结 ACK 信封 → 平台 `handle_robot_ack` →
   任务状态推进 + `t_task_ack` 落账；再模拟进程重启（新建 AckTracker +
   `rebuild_ack_tracker`）后重放同一回执，断言：
   - 任务**不再**重复推进；
   - 账本 `duplicate_count` 递增且首次规范回执未被覆盖；
   - 身份不一致 / 未知任务 / 未登记 deadline 等负例仍按 WP-14C 语义拒绝，
     且不污染 tracker、不写账本。
   用例必须能在有 PostgreSQL 时走真实 scratch 库；无数据库时按既有模式
   `pytest.skip` 并明确说明，不得用内存假设冒充实库结论。
4. 文档同步：`docs/device-interface.md` 记录设备序号持久化与重启语义；
   `docs/mqtt-topics.md` / `docs/architecture.md` 记录启动恢复行为与其边界
   （`late` 判定对「发布后未 ACK」命令重启后仍不可恢复 —— 必须如实写明，
   不得宣称完整恢复）。
